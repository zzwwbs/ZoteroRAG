# Story 1.4: Extract Text from Attached PDFs

## Status
- Done

## Story
**As a** user,
**I want** the app to identify PDF attachments for Zotero items and extract their text content using PyMuPDF,
**so that** the text can be prepared for indexing.

## Acceptance Criteria
1.  For each Zotero item with a PDF attachment, the application can locate the PDF file in the `storage/` directory.
2.  The application successfully extracts text content from a sample PDF using PyMuPDF.
3.  The application logs errors for PDFs from which text extraction fails, but continues processing other PDFs.
4.  The extracted text is available for subsequent processing steps.

## Dev Notes
This story focuses on adding the capability to extract raw text from PDFs linked in the Zotero database. The core logic should be encapsulated in a dedicated, testable utility function and then integrated into the `indexing_service`.

- **Project Structure:**
  - New PDF extraction logic should be placed in a new utility file: `src/zoterorag/core/utils/pdf_extractor.py`. [Source: `unified-project-structure.md`]
  - The orchestration of this extraction will be handled by the existing `src/zoterorag/core/services/indexing_service.py`. [Source: `backend-architecture.md`]
- **Technology:**
  - Use `PyMuPDF` for PDF text extraction. This is a new dependency that needs to be added to `pyproject.toml`.
  - Use the standard Python `logging` module for error reporting. [Source: `tech-stack.md`]
- **Data Models:**
  - This story precedes the creation of the `Chunk` model. It operates on the file path associated with a Zotero item and produces a raw text string. The `Document` model's `pdf_file_path` attribute is relevant here. [Source: `data-models.md`]
- **Error Handling:**
  - It is critical that the application does not halt if a single PDF is unreadable. Errors must be logged, and the process should continue with the next available PDF.

## Testing

### Critical Bugs Found and Fixed

**Bug #1: Incorrect Database Column Name**
- **Issue**: Query used `sourceItemID` instead of `parentItemID`
- **Impact**: Complete failure to retrieve attachments from real Zotero database
- **Root Cause**: Test mocks used incorrect schema that didn't match production Zotero
- **Fix**: Changed SQL query to use correct `parentItemID` column
- **Files Modified**: `src/zoterorag/core/services/zotero_manager.py`, `tests/test_zotero_manager.py`

**Bug #2: Storage Path Resolution**
- **Issue**: Path `storage:filename.pdf` not resolved to actual location
- **Impact**: PDFs could not be located even when query succeeded
- **Root Cause**: Zotero uses key-based subdirectories: `storage/{attachment_key}/{filename}`
- **Solution**: 
  - Modified query to JOIN with `items` table to get attachment key
  - Updated `_resolve_attachment_path()` to use attachment key as subdirectory
  - Changed path resolution: `storage/{key}/{filename}` instead of `storage/{filename}`
- **Files Modified**: `src/zoterorag/core/services/zotero_manager.py`, `tests/test_zotero_manager.py`
