## Dev Notes

This story orchestrates several components built in previous stories into a cohesive indexing workflow. The primary implementation will be a new `IndexingService`.

### Proposed File Structure
- **New Class:** `IndexingService`
- **Location:** `src/zoterorag/core/services/indexing_service.py`

This aligns with the project's architecture for housing core business logic.

### Dependent Component Summary
The `IndexingService` will coordinate the following existing functionalities:

1.  **Text Extraction (Story 1.4):** Uses `PyMuPDF` to extract text content from PDF files located in the Zotero `storage/` directory.
2.  **Text Chunking (Story 2.2):** A utility function that breaks down text into ~600 token segments with a ~100 token overlap, using sentence boundaries where possible.
3.  **Embedding Generation (Story 2.3):** A client that sends text chunks to a cloud embedding API (e.g., OpenAI) and retrieves the vector embeddings.
4.  **Data Storage (Story 2.1):** A repository layer that manages storing vector embeddings in a local `FAISS` index and their corresponding metadata (document ID, chunk text, etc.) in a local `SQLite` database.

### Incremental Update Logic
To meet AC #2.5.4, the `IndexingService` must check the `SQLite` database to see if a Zotero item (and its specific attachment) has already been processed. A simple way is to check for the existence of the document's ID in the metadata store before initiating the text extraction step.

### UI Progress Reporting
To satisfy AC #2.5.3, the `IndexingService` should use PySide6's signal/slot mechanism to emit progress updates. The main UI window will connect a slot to this signal to update the view.

- **Signal:** `progress_updated`
- **Signal Data Payload (dict):**
  ```python
  {
      "processed_count": int,
      "total_count": int,
      "current_item_name": str,
      "status": "processing" | "error" | "complete",
      "error_message": str | None
  }
  ```
