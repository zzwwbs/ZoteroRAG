# Story 5.2: Implement Secure API Key Management

## Status
- Done

## Story
**As a** user,
**I want** my API keys to be stored and used securely,
**so that** my credentials are protected from unauthorized access.

## Acceptance Criteria
1.  5.2.1: API keys are encrypted at rest using an appropriate, platform-specific method (e.g., OS keychain, encrypted file via the `keyring` library).
2.  5.2.2: API keys are never exposed in plain text in logs or configuration files.
3.  5.2.3: The application only accesses API keys when actively making an API call.
4.  5.2.4: Users are clearly informed about how their API keys are stored and used (Note: This will be primarily handled in UI stories 5.4 and 5.5, but the backend should not prevent this).

## Dev Notes
This story is critical for application security and user trust. The implementation must strictly adhere to the principle of never storing or logging API keys in plain text.

- **Previous Story Insights**: The robust logging and error handling framework from Story 5.1 must be used. Any failure during key storage or retrieval (e.g., `keyring` backend not available) should be logged with `logger.exception()` to `debug.log` without exposing any sensitive information. [Source: `docs/stories/5.1.Implement-Comprehensive-Error-Handling-Logging.story.md`]

- **Data Models**: No new data models are introduced. This story focuses on application configuration. [Source: `docs/architecture/data-models.md`]

- **File Locations**:
    - The primary logic will be implemented in `src/zoterorag/config/settings_manager.py`. [Source: `docs/architecture/unified-project-structure.md`]
    - Tests will be located in `tests/config/test_settings_manager.py`. [Source: `docs/architecture/unified-project-structure.md`]

- **Technical Constraints**:
    - The `keyring` library is mandatory for interacting with the OS credential manager. [Source: `docs/architecture/security-risk-and-mitigation.md`]
    - API keys must never be stored in plain text files or logs. This is a strict security requirement. [Source: `docs/architecture/security-risk-and-mitigation.md`]
    - The application should gracefully handle cases where the `keyring` backend is unavailable, logging the error and proceeding as if no key were set.

- **Auth Flow**: The implementation should follow the prescribed authentication flow for external APIs. The `SettingsManager` is responsible for retrieving the key from the OS credential store. [Source: `docs/architecture/backend-architecture.md#auth-flow-external-api`]

### Testing
- **Testing Standards**:
    - Unit tests are required for all new logic in `SettingsManager`.
    - Use `pytest` as the testing framework. [Source: `docs/architecture/tech-stack.md`]
    - **Crucially**, for testing purposes, the `keyring` backend must be mocked or set to an in-memory backend (`keyring.backends.memory.Keyring`) to prevent tests from interacting with the actual OS keychain and to ensure tests are hermetic. This setup should be done in the test file itself or a `conftest.py`.

### Code Quality Assessment

**1 CRITICAL SECURITY BUG FOUND AND FIXED** ⚠️✅

Story 5.2 implements secure API key management using OS keyring, but **a critical security vulnerability was discovered** during QA validation where API keys could leak to plaintext configuration files.

**Bug Found:**
- **BUG-001 (CRITICAL - SECURITY)**: API keys leaked to plaintext config when using keyring
  - **Location**: `src/zoterorag/config/settings_manager.py`, line 143
  - **Issue**: `set_api_key_securely()` stored plaintext key in `self._settings.api_key` after successful keyring storage. Later calls to `set_enable_ai_analysis()` or `set_zotero_path()` would write this plaintext key to disk via `save_settings()`.
  - **Impact**: Violated AC 5.2.2 - API keys were exposed in plaintext in `settings.json`
  - **Root Cause**: In-memory `self._settings` held plaintext key after keyring storage
  - **Fix**: Changed line 143 from `api_key=api_key` to `api_key=None` to prevent plaintext storage in memory
  - **Verification**: Added regression test `test_api_key_not_leaked_to_plaintext_config_when_using_keyring`
  - **Status**: ✅ FIXED

**Strengths After Fix:**
- Keyring integration properly implemented
- API keys encrypted at rest using OS credential store
- Graceful fallback when keyring unavailable
- Error logging never exposes API keys
- Services correctly use `get_api_key()` for secure retrieval
- Comprehensive test coverage with dummy keyring backend

### Refactoring Performed

**Security Fix Applied:**
- **File**: `src/zoterorag/config/settings_manager.py`
  - **Change**: Line 143: `api_key=api_key` → `api_key=None`
  - **Why**: Prevent plaintext API key from being stored in memory after keyring storage, which would leak to disk when other settings are saved
  - **How**: Setting `api_key=None` in `self._settings` ensures no plaintext key persists in memory. The key is only stored in the OS keyring and retrieved when needed via `get_api_key()`.

**Regression Test Added:**
- **File**: `tests/config/test_settings_manager_keyring.py`
  - **Test**: `test_api_key_not_leaked_to_plaintext_config_when_using_keyring`
  - **Purpose**: Verifies that storing a key in keyring and then modifying another setting does NOT write the API key to plaintext config file
  - **Coverage**: Ensures fix prevents future regressions of this critical security issue
