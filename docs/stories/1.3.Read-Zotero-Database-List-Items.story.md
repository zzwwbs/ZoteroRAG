# Story 1.3: Read Zotero Database & List Items

## Status
- Done

## Story
**As a** user,
**I want** the app to **read my Zotero database in read-only mode and display a list of my library items**,
**so that** I can see my Zotero data within the app.

## Acceptance Criteria
1.  1.3.1: The application successfully connects to the `zotero.sqlite` database in read-only mode.
2.  1.3.2: The application can retrieve and display a list of Zotero items (e.g., title, author, year).
3.  1.3.3: The application handles cases where the Zotero database is locked or corrupted gracefully, displaying an informative error.
4.  1.3.4: No write operations are performed on the `zotero.sqlite` database.

## Dev Notes

### Previous Story Insights
- Story 1.2 established the `ZoteroManager` and `SettingsManager`. This story will extend the `ZoteroManager` to perform its primary function of reading data from the Zotero database. The `SettingsManager` will provide the path to the database.

### Architecture & Technical Details
- **Workflow:** This story continues the "Initial Setup & Indexing Workflow". After the Zotero path is known, the app needs to read from it. [Source: `docs/architecture/core-workflows.md`]
- **Component Interaction:**
    - The `ZoteroManager` will be responsible for all database interactions. It will receive the database path from the `SettingsManager`.
    - A new UI view, `LibraryView`, will be created to display the items.
    - The `MainWindow` will instantiate the `LibraryView` and pass it the data retrieved from the `ZoteroManager`.
- **Key Components:**
    - `ZoteroManager`: Will be expanded to include methods like `get_all_items()`. It must use the `sqlite3` module to connect to `zotero.sqlite` in read-only mode by using the `uri=True` and `mode=ro` connection flags. It will query the `items`, `itemData`, `creators`, and `itemCreators` tables to fetch the required data. [Source: `docs/architecture/components.md#zoteromanager`]
    - `LibraryView`: A new UI component to display the list of items. It should use a `QTableView` with a `QAbstractTableModel` for efficient data handling. [Source: `docs/architecture/frontend-architecture.md#component-organization`]
- **Data Models:**
    - The data retrieved from Zotero should be mapped to the application's internal `Document` data model as much as possible. For this story, a simplified representation is acceptable. [Source: `docs/architecture/data-models.md#document`]
- **File Locations:**
    - `ZoteroManager` modifications: `src/zoterorag/core/services/zotero_manager.py`
    - New UI View: `src/zoterorag/ui/library_view.py`
    - `MainWindow` modifications: `src/zoterorag/ui/main_window.py`
- **Error Handling:**
    - The connection logic must be wrapped in a `try...except sqlite3.OperationalError` block to handle locked or corrupted database files, as per AC 1.3.3.
- **Testing Requirements:**
    - Unit tests should be created for the `get_all_items()` method in `ZoteroManager`. This will require a mock `zotero.sqlite` file or mocking the `sqlite3` connection and cursor.
    - Manual testing should verify the full UI flow.
