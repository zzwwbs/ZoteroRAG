### Story

**As a** developer,
**I want to** replace the `pdfplumber`-based text extraction with a `pypdfium2`-based implementation,
**so that** the application's PDF processing is faster and more efficient.

---

### Acceptance Criteria

1.  11.1.1: All code referencing `pdfplumber` is removed and replaced with `pypdfium2` equivalents.
2.  11.1.2: The application successfully extracts text content from a sample PDF using `pypdfium2`.
3.  11.1.3: The application logs errors for PDFs from which text extraction fails but continues processing other PDFs.
4.  11.1.4: The extracted text is available for subsequent processing steps in the same format as the previous implementation.

---

### Dev Notes

This story involves migrating from `pdfplumber` to `pypdfium2` to improve performance. All changes should be focused on the PDF extraction logic within the `indexing_service`.

**Previous Story Insights**:
*   The previous migration (Story 10.1) centralized all PDF text extraction logic into `src/zoterorag/core/services/indexing_service.py`. This is the primary location for the changes. [Source: Story 10.2]
*   A benchmarking script exists at `scripts/benchmarking/benchmark_pdf_extraction.py` which was used to validate the `pdfplumber` migration. This script should be updated or used to verify the performance of `pypdfium2`. [Source: Story 10.2]

**File Locations**:
*   **Primary file for modification**: `src/zoterorag/core/services/indexing_service.py`. The function responsible for PDF extraction will be updated here. [Source: `docs/architecture/backend-architecture.md`]
*   **Dependency Management**: The `pyproject.toml` file will need to be updated to remove `pdfplumber` and add `pypdfium2`. [Source: `docs/architecture/unified-project-structure.md`]

**Technical Constraints**:
*   The output of the new `pypdfium2`-based extraction must be a single string containing the entire text of the PDF, identical to the format provided by the previous `pdfplumber` implementation, to ensure compatibility with downstream chunking logic.
*   The new implementation must handle potential errors during PDF parsing gracefully, logging the error and allowing the indexing process to continue with the next file. This aligns with the robustness tests added in Story 10.2.

**Testing Requirements**:
*   **Unit/Integration Tests**: The existing tests for the indexing service, particularly those in `tests/core/services/test_indexing_service.py`, must pass with the new `pypdfium2` implementation. [Source: `docs/architecture/testing-strategy.md`]
*   The robustness test `test_indexing_service_handles_corrupted_pdf_and_continues` is especially important to validate for AC 11.1.3.
*   The existing test `test_extract_text_from_pdf_returns_expected_string` in `tests/core/utils/test_pdf_extractor.py` (or its equivalent for the indexing service) will need to be validated against the output of `pypdfium2`.
